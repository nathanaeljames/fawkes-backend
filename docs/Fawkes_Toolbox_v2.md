## Appropriations and personal decisions (how we use the tools)

**Context layers (adopted from MemPalace, rebuilt).** Each layer is defined by *what* it carries and by *how* it is fetched. MemPalace's own stack, for the record: L0 identity (~50-100 tokens, always loaded), L1 the top critical memories across the palace (team, projects, preferences; ~120-800 tokens depending on the version described, always loaded), L2 room recall — context for the current topic pulled from the relevant wing and room, on demand when the topic comes up — and L3 deep search across everything, only when explicitly asked; its L2 and L3 are on demand because the agent (or the human, with local models) decides to call a search tool, while the search itself is deterministic code. Fawkes keeps the *what* and changes the *how* where the voice loop demands it.
- *Layer 0* — what: persona (core directives, voice register, behavioral boundaries) and the tool registry for the slot. How: static text, byte-stable, prompt-cached, warmed once at boot, identical on every turn.
- *Layer 1* — what: per-user standing context: promoted durable facts about the identified speaker, their active projects and goals, and — during research sessions — the research status board. How: SQL keyed on user_id when ECAPA resolves identity (mid-session if identification arrives late); the status board refreshed at every loop boundary.
- *Layer 2, project slice* — what: recent sessions of the active project, as verbatim recent turns under a token cap (2-4K tokens as a placeholder, set by the harness's recall slice), with sessions older than the cap represented by their idle-window summaries plus pointers that Layer 3 can expand to verbatim. Verbatim is the default because the research (MemPalace's raw-mode 96.6% vs 84.2% compressed; Mem0/Zep summary losses) establishes it; the constraint is the token cap, not fidelity. How: SQL keyed on project_id, loaded once when the active project resolves (active project in Layer 1 or explicit command), refreshed at session boundaries, placed in the cache-stable prefix region after Layer 1 so it costs prefill once per session.
- *Layer 2, topic slice* — what: memories relevant to the current utterance from the request's silo, weighted toward the active project. How: hybrid BM25+vector with Reciprocal Rank Fusion over the *whole* finalized utterance — no keyword-selection step; Postgres stems, drops stop words, and weights surviving terms by rarity, and the vector side embeds the utterance once — run by deterministic code before any model call, only on escalated turns, tens of milliseconds. Deterministic sharpeners permitted without a model call: dictionary matching against ontology entities (known people, projects, tools) to trigger exact fact lookups; appending the previous user turn for pronoun-heavy utterances. *Frozen-snapshot rule*: the topic slice is injected into this turn's prompt in a capped slot (top 5-8 snippets, a few hundred tokens) placed after the cached prefix, used for this turn, discarded on the next; only the verbatim dialogue persists in the window, so retrievals never accumulate.
- *Layer 3* — what: anything beyond the standing and per-turn slices: whole-silo transcript search (full-text or trigram), fact lookups with SQL joins, document-node lookup, research-transcript access. How: LLM-invoked single-shot tools on demand only; on the voice path, fast-class tools only and at most one tool round (see the latency policy below). In both MemPalace and Fawkes the deep search executes as deterministic code and the decision to invoke it belongs to the model or the user; the only asymmetry is at Layer 2, where MemPalace's trigger is the agent and ours is code.
- Outside the numbering, per turn: active FSM state and slot schemas, local time, elapsed time since the previous turn.

**Organization (replacing MemPalace's wings/rooms/halls).** Wings → **projects** (scope keys on every row; project management UI in Phase 5). Rooms → **topics** within a project, emergent, not pre-created. Halls → replaced by the **facet taxonomy**: fact / preference / decision / event / task-state (approved 2026-09-24; a starting set, extended via ontology versions; candidate extensions noted and not adopted: insight for MemPalace's discoveries, advice for its recommendations). For the record: the MemPalace article read together (Dunham, April 2026) described the shipped halls as Travel / Work / Health / Relationships / General — consumer defaults we discarded — while the repository README lists them as facts (locked-in decisions), events (sessions, milestones, debugging), discoveries (breakthroughs), preferences (habits, opinions), and advice (recommendations); its miner uses a separate five-type classifier (decision, preference, milestone, problem, emotional). Tunnels → tunnels, within one silo only. Scopes act as **soft weights** on retrieval scores, never hard filters, except where row-level security demands isolation between users and except for silos, which are hard partitions.

**Partitioning, three mechanisms kept distinct.** *Silos* are hard partitions of data: every row carries one silo, tunnels cannot cross, caches and prompts are keyed and asserted, and the schema works with many silos per database or one silo per database. Tier A (migration 001, about an hour, no runtime cost): the silo key on every row, in every unique constraint and index prefix, composite project references, single-silo tunnels, per-silo content hash, silo context on every call, leakage tests. Tier B (first real second silo): partitioning by silo, silo-keyed forced row-level security, per-silo roles, instance pin. *Project scopes and tunnels* are soft ranking weights inside a silo (wings → projects, rooms → topics, halls → the facet taxonomy). *Row-level security* is per-user authorization inside a silo (user-keyed in Phase 5 regardless). Identity (speakers, imprints, devices) lives outside silos with a membership table and a default silo per user. Fawkes runs one silo; the key is the glue that lets one codebase serve many-silos-per-database and one-silo-per-database deployments alike, so that a hardened deployment needs infrastructure, not code changes. An owner change about projects that do not live in silos is pending (Specification Q-09); nothing here changes until it lands.

**Tunnels (MemPalace's idea, our lifecycle, within a silo).** Propose (autonomously when cross-project relevance is high or local context sparse, always attributed and flagged on first use) → cross on explicit command → reinforce on repeated use → decay on veto ("don't factor that in") → destroy on request ("never connect these"). Layer-1 standing-context matches form weak provisional tunnels.

**Recall ladder (Hermes/SimonScrapes/GBrain synthesis).** Standing context → hybrid BM25+vector with Reciprocal Rank Fusion → rerank → context expansion to neighboring turns → cited synthesis, or an honest "not found." Verbatim text is what gets cited; summaries are never the source of truth.

**Voice-path latency policy (2026-09-25; every figure tentative pending measurement).** Hops are counted by who takes them: *SQL hops* (joins inside one deterministic query over the facts table; indexed self-joins stay fast through three to four hops at our scale, expressiveness degrading before speed) are voice-path work; *reasoning hops* (a model reads results and decides the next query; ~0.5-1 s each even on GPU) are research work by definition. Budgets: *Budget A*, pre-LLM assembly of Layers 0-2 by deterministic code, ~150 ms (the Phase 2 exit figure — never a whole-turn number); *Budget B*, one voice-path tool round, ~500 ms wall clock, with fast-class tools executed in parallel (the structured-output contract's `tool_calls` field is plural); beyond B, stall word ("let me look deeper into that, but here is what I can say for now"), provisional answer, research task, correction back by voice. Every registered tool carries a *latency class*: fast (SQL fact and join lookups, full-text and trigram search over transcripts, document-node fetch, semantic-cache lookup, single-shot lookups such as weather, timers, reminders, fact storage and recall) or slow (LLM-guided document-tree descent, web search, multi-document synthesis, anything multi-step); the voice slot's registry exposes fast tools only; the voice path allows at most one tool round per turn; the structured output either answers or requests research, with a low confidence field plus weak Layer 2 hits as the trigger. Document trees: node lookup (fetch a section by id or title, full-text over node summaries) is SQL and milliseconds and is a fast voice tool; LLM-guided descent is multi-second and research-only. Whole-turn estimates to be measured: ~0.5-1 s to first audio for a no-tool turn, ~1.5-2.5 s for a one-tool-round turn. Retrieval costs with a warm cache: HNSW 1-10 ms, GIN full-text 1-20 ms, fusion negligible; the query embedding (bge-m3 on CPU ~50-200 ms, on GPU ~5-10 ms) dominates. *Warm cache* means the index and table pages have been read into Postgres's shared_buffers or the OS page cache since the last restart; eviction is by memory pressure (model loads, the speech stack, large ingests), not by a timer; so shared_buffers is sized to the indexes and pg_prewarm runs at startup. Distinct caches, never conflated: Postgres's page cache, the application semantic cache (C-14), and vLLM's prefix cache in VRAM.

**Ingestion contract (Sudip P.'s event bus, without the bus).** One `ingest()` entry point; content hash unique per silo + timestamps + provenance + silo and project stamps; idempotent per-store handlers (transcripts, facts, FTS, vectors, trees, wiki); turns, traces, and model-call cost rows enter the same way. Swap the internals for a real bus (Redis Streams/NATS) when multi-process, without changing callers. What we took from Sudip: the relational store is the only system of record; one write fans out to every derived store; reconciliation sampling checks that stores agree; a graph database is added only when a real multi-hop query demands it; a segmented eval harness precedes any new store.

**Receipts (MNEMOS contracts, extended).** Manifest rows on every summarization/compression/archival; trace records on every retrieval; tokens and cost on every model call (Plano-style span attributes); versioned ontology migrations; nothing silently rewritten.

**Timestamp policy.** Every timestamp is a full date-time stored as UTC `timestamptz`. Every device and web session registers an IANA time zone on connect (the default is a deployment setting, not a documented value); the prompt builder renders local time and elapsed-since-previous-turn per session. No naive timestamps, no local-time storage.

**Input routing doctrine (three channels; the anti-Rasa).** (1) Voice: all ASR text → 4B router → {ignore | FSM event (+slots, tiny in-workflow replies rendered by the router) | escalate to the voice-slot model}; almost everything not dropped or FSM-bound is escalated; the router is the primary FSM driver, and the voice-slot model may also propose transitions that need conversational context or that the router missed. ASR text never reaches the research pipeline except through the voice pipeline. (2) Text (web/app): all text → 4B as arbiter → {dispatch to research now | queue for next loop boundary | interrupt running task | FSM command}; never discard; ~5 s default-to-queue timeout; illegal FSM commands return to the arbiter. (3) Rubber-duck powers: the voice-slot model may answer, write a blackboard note, or issue start/queue/interrupt imperatives directly to the research command queue. Response modality follows input modality. The deterministic validator ratifies every proposed transition and returns rejections to the proposer with a hint, bounded; coughs and fragments that leak past VAD land in the ignore class.

**Dual-pipeline interplay (our design).** *Notes-up*: distilled context flowing from the voice pipeline up into the research pipeline's blackboard (voice → research, filtered). *Read-down*: research state flowing down to the voice pipeline — a status board refreshed at every loop boundary into voice Layer 1, plus deep access to the full research transcript via voice Layer 3 tools (research → voice; the voice pipeline can always speak intelligibly about what the researcher is doing without carrying a copy of its context). *Imperative channel*: explicit commands from voice or text that execute actions in the research pipeline (start, queue, interrupt) rather than merely adding context. Machinery: asyncio inbox queue, pending counter, a condition the research loop waits on at each boundary (with timeout), and a watcher task that cancels generation on interrupt. The research model — never the arbiter — decides how to resteer.

**Serving policy.** The OpenAI-compatible endpoint is the seam; the engine behind it is chosen by the eval harness per role: short-context, high-concurrency work (voice turns, agent fan-out) favors a speculative-decoding vLLM configuration; deep-context research favors a steady engine that does not depend on drafter acceptance. Two cards default to one model per card. Tensor parallelism is an experiment, not a plan. A throughput number is recorded with the prompt and context depth that produced it.

**Capability cards.** One versioned row per (model, quantization, serving config) in `capability_cards`, written by the eval harness: per-slice accuracy (FSM routing, voice recall, research multi-hop, coding patch, structured-output validity), latency percentiles at stated context depths, tool-call validity rate, loop rate, stop-compliance rate, cost per task. The router reads cards for escalation thresholds; the external bridge reads them for tier selection; a card revision that regresses a slice opens a review.

**Capability cards, how they are measured.** Deterministic scoring wherever possible: labeled routing verdicts (exact match), seeded recall facts (answer contains fact and cites expected turn), fixed-corpus multi-hop (expected citation ids), coding patches (apply to a failing-test repository and run the suite), schema validation, loop/stop/latency observed by the harness; a reference-anchored LLM judge only for free-text slices. The seed set is fixed; the run is keyed by a fingerprint of model, quantization, serving configuration, prompt version, and index contents, skipped when unchanged, repeated over several sampling seeds with a confidence interval, scheduled into idle windows plus a weekly sanity run. A slice is one task family with its own seed cases, scoring rule, and score; each model is carded only on the slices its slot serves (router: routing, extraction; voice slot: recall, everyday answering, register, tool-call validity; research slot: multi-hop, coding patch, structured output; remote tiers: research-tier slices only, never routing or recall). Cadence: nightly ~10-case smoke subset; full run on fingerprint change and weekly; coding-patch slice weekly from Phase 3 (hand-authored micro-repositories under `tests/eval/repos/`, optionally a small HumanEval+/Aider-polyglot subset); remote tiers once per release plus a monthly capped spot-check. Real-usage corrections, re-asks, and thumbs are captured in `feedback_events` (schema from Phase 1, filled by voice in Phase 2 and web in Phase 5) and become new labeled cases. Cards are absolute per model; comparison falls out of shared tasks. Panel mode is a runtime feature, but every panel run records per-model tokens, loops, compute time, and judge rubric grades to `panel_results`, summarized onto cards as field observations labeled uncontrolled.

**Routing to remote models (external API bridge).** Order of decision: explicit user request → task criticality flag → local confidence (the structured-output confidence field, treated as a weak signal) cross-checked by cheap verification (sample agreement, verifier/judge pass, test-harness result where applicable) → complexity estimate (length, tool needs, multi-step markers, domain) → budget. Capability cards for every local and remote model are written from segmented eval results, never from vendor tables, and revised on fingerprint change and weekly. Payloads outward are extracted text, JSON, or Markdown; documents and images stay local unless visual judgment is the task.

**Panel mode (decorrelated judgment; from the Greek-tutor porting pipeline and Fusion patterns).** Two grades: identical-spec parallel execution with an arbiter (judge-selects verbatim, vote, synthesize, test-harness-wins), and decision-point consensus where only extracted key decisions are cross-checked. Every fan-out records which models ran, each candidate, and the verdict. Reserved for complex, critical, or sensitive tasks; available inside heads-down mode; Qwen self-fusion (multiple samples) available before Gemma exists.

**Thinking policy.** Same weights, per-request settings: voice runs thinking off or with a small budget; research runs thinking high with thinking preservation. Gemma, when present, adds register and decorrelated judgment, not a different thinking policy.

**Diagram conventions (house colorway, semantics assigned).** Colors mark logic roles, not component types: `action` (green) = LLM inference nodes; `handler` (brown) = deterministic processing code; `decision` (orange diamond) = deterministic dispatch/branch points; `server` (grey cylinder) = data stores and services; `form` (blue) = pipelines and subsystems shown as a unit; `startEnd` (thick green stadium) = entry/exit. Shapes: cylinder = store, diamond = branch, stadium = entry/exit, rectangle = process; dotted edges = load-once/startup relationships or retry-returns. Subgraphs mark pipeline boundaries; a labeled edge crossing a subgraph is a deliberate crossing. **Complexity levels:** 1 = five boxes; 4 = README (a visitor grasps it in ten seconds; ~15-20 nodes, one store, no retry loops, only sanctioned crossings); 7 = engineering reference (~35 nodes, subgraphs, every crossing labeled); 10 = exhaustive (every component and pathway in the specification, one node per moving part). Sources: `docs/diagrams/architecture_L4.mmd`, `_L7.mmd`, `_L10.mmd`; the README embeds an exported image of L4.

**Public-documents hygiene.** Project documents contain no secrets, hostnames, credentials, employer names, or third-party personal names; deployment defaults (time zone, ports, paths) live in configuration; design notes that reference an employer or a compliance context stay out of the public repository; secret scanning runs on every push; `.env`, `api_key.txt`, and model directories are gitignored.

**Document discipline (2026-09-24).** Project documents are cumulative: recorded detail leaves a document only when the owner removes it, a later decision supersedes it, or it is shown to be wrong. Every regeneration is diffed against the previous version and every removal itemized as a deliberate supersession; a regeneration with no removal list may remove nothing. New versions carry a new version suffix. The repository copy is the reference version; the Claude Project's uploads are refreshed from it after every commit.

**Ontology v1 sketch (Phase 1 deliverable as `ontology.md`).** Entities: Silo, Person (user), Device, Project, Conversation, Turn, Document, DocumentNode, Fact, Task, Tool, ModelCall, CapabilityCard, FeedbackEvent, PanelResult. Relations (domain → range): spoke (Person→Turn), belongs_to (Turn/Document/Fact/Task→Project→Silo), cites (Fact→Turn/DocumentNode), supersedes (Fact→Fact), prefers / decided / scheduled (Person→Fact by facet), assigned_to (Task→Person), produced_by (Turn→ModelCall), member_of (Person→Silo). Every Fact carries facet (v1: fact, preference, decision, event, task-state), valid_from, valid_to, recorded_at, source, silo_id. Rule: a type or relation earns its place only with a concrete query behind it; start strict.
