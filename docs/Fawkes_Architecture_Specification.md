## 0. Purpose and scope

Fawkes is a self-hosted, voice-native, multi-user AI assistant. It listens on any microphone or client, identifies the speaker by voice, remembers every conversation verbatim with timestamps, reasons over that memory with a hierarchical state machine driving local language models, and runs a separate research/coding pipeline alongside the voice loop. Everything runs on owned hardware; cloud calls are explicit, budget-gated, and logged.

## 1. Hard requirements

- R-01 Multi-user and multi-endpoint at every stage: memory is keyed to resolved speaker identity, never to a session.
- R-02 Verbatim, timestamped storage of every turn (both roles), every fact, every resource; time stored as UTC with time-zone-aware types; per-session time zone; elapsed time rendered into prompts.
- R-03 One ACID system of record (Postgres); all other stores derived and rebuildable.
- R-04 Two latency classes: the voice loop performs only deterministic lookups, cached answers, and single-shot hybrid retrieval; reasoning-driven retrieval belongs to the research pipeline. Two kinds of hop are distinguished: SQL hops (joins inside one query over the facts table; deterministic, milliseconds; indexed self-joins stay fast through three to four hops at Fawkes scale, expressiveness degrading before speed) are permitted on the voice path; reasoning hops (a model reads results and decides the next query; roughly 0.5-1 s each even on GPU) are research-pipeline work by definition. Voice-path budgets, tentative pending measurement at Milestone Zero: Budget A, pre-LLM assembly of Layers 0-2 by deterministic code, at most ~150 ms; Budget B, one voice-path tool round with fast-class tools executed in parallel (C-09), at most ~500 ms wall clock; beyond Budget B the voice slot answers provisionally and hands off to research (P-05). Neither budget is a whole-turn figure; time to first audio is estimated at ~0.5-1 s for a no-tool turn and ~1.5-2.5 s for a one-tool-round turn, to be measured.
- R-05 The LLM proposes; deterministic code ratifies every state transition.
- R-06 Tools, memory, transcripts, and web access are bound to pipeline slots, not to models.
- R-07 Every transformation writes a manifest; every retrieval writes a trace; every model call records tokens and cost.
- R-08 Answers about the past cite sources or admit ignorance.
- R-09 Outbound cloud payloads are extracted text and structured data unless visual judgment is the task.
- R-10 Nothing from the ASR channel reaches the research pipeline except through the voice pipeline; nothing from text channels is discarded.
- R-11 Every content row belongs to exactly one scope — a workspace, a user, or a silo — carried as a scope kind and scope id; silos are hard partitions that no tunnel, ranking weight, cache, or prompt may cross; the schema supports many silos per database and one silo per database without code changes. Enforcement machinery beyond the key (partitioning, silo-keyed row-level security) is added when a second silo exists. (Supersedes the 1.4 wording "exactly one silo key"; projects may now live in any scope, which resolves former Q-09.)
- R-12 Access is tiered by assurance level: workspace (registered-device trust, no authentication), user (voice authentication with a pushed rotating pass-passage read aloud, device biometrics, or web sign-in), silo (a live web or app sign-in plus a PIN as second factor, device-exclusive, short timeout). Authorization is evaluated per utterance against continuous speaker identification, never granted to a device for a session as a whole. Writes to a user's own store require only high-confidence continuous identification; reads from it require user authentication (owner answer 2026-09-26).

## 2. Model slots and hardware

- S-01 Router/arbiter slot: Qwen3-4B-Instruct class, served by llama.cpp. Roles: voice-channel routing, text-channel arbitration, mid-flight injection triage, slot extraction, memory-promotion judgments, background summarization. Upgrade path: 14B-class utility model if evals demand.
- S-02 Voice slot: the model that answers escalated voice turns. Qwen3.8-27B (thinking off or small budget) through Phase 3; Gemma 4 from Phase 4. Powers: answer; call single-shot tools; propose FSM transitions from conversational context; write a blackboard note; issue start/queue/interrupt imperatives to the research command queue.
- S-03 Research slot: Qwen3.8-27B (thinking high, thinking preservation), served by vLLM behind an OpenAI-compatible endpoint. Drives the research/coding pipeline; performs its own resteering.
- S-04 Embedding model: bge-m3 class (CPU until second GPU). Reranker: bge-reranker-v2-m3 class (optional).
- S-05 External models: Anthropic API models via the external API bridge (C-22); tier selected from capability cards per the routing policy.
- S-06 Heads-down mode (Phase 4+): the voice-slot GPU allocation may be swapped for a second coding model or a retrieval specialist (Harness-1); the voice slot then falls back to a Qwen register; panel mode remains available.
- H-01 Phase 1 (one RTX 3090, text-mode): vLLM at ~0.80 utilization for the 27B Int4 plus KV cache; 4B under llama.cpp on the same card; embedder on CPU. Fallback: split mode, alternating loads per eval slice. Optimized serving recipes (tuned vLLM fork with a draft model; tuned llama.cpp fork for long context) are measured against stock vLLM by the eval harness, never assumed.
- H-02 Phase 2 (one card): speech stack + 4B resident; FSM voice flows on the 4B alone; 27B swapped in for open conversation when no speech session needs the stack.
- H-03 Phase 4 (two cards): the default layout pins one model per card (card one = research slot; card two = speech stack + voice slot) for isolation and predictable latency. Tensor parallelism across both cards is an experiment permitted only with a verified NVLink bridge, x16 slots, and PSU transient headroom, and adopted only if the eval harness shows a single-stream or capacity gain that the voice pipeline's latency does not pay for.

## 3. Components

- C-01 Audio I/O and WebSocket layer. Streams audio per client; tracks device id and registered IANA time zone. Carry-over.
- C-02 VAD and endpointing (MarbleNet). Detects speech, finalizes utterances, drops most non-speech. Carry-over. Front-end seam (2026-10-06): the audio front end exposes each utterance in two forms — the raw capture and, when enhancement is enabled, an enhanced copy (denoise, dereverberation) — and every consumer declares which it takes: ASR may consume the enhanced form; the speaker matcher consumes the raw form unless an A/B on the identification slice proves otherwise, because enhancement removes speaker cues along with noise. Enhancement models are therefore pluggable per consumer, never a global stage.
- C-03 ASR (interim FastConformer; final Canary-Qwen; SSM replacement ~Phase 3.5). Carry-over. Interface contract (2026-10-06, so the SSM swap and later per-speaker heads are substitutions rather than rewrites): a typed streaming interface with `open_stream(stream_id, options) → state`, `feed(state, audio) → interim hypotheses`, `finalize(state) → final hypothesis`, where the per-stream state object is opaque (a transformer's cache or a state-space model's fixed hidden state both fit); optional N-best output for rescoring; an optional speaker-conditioning input (an embedding or adapter id) so a speaker-dependent head can be plugged in without changing callers; one state per stream, so parallel per-speaker heads are N states, not N models. This interface is outside X-01 (speech is not chat-completion traffic).
- C-04 Speaker identity (ECAPA-TDNN). In-memory embedding matrix built from Postgres at startup and updated on enrollment; per-second matching; emits user_id with confidence; supports deferred identification tiers. Per-thread accumulator (adopted 2026-09-27): iteration 1 scored each utterance alone, so five four-second utterances never produced a five-second identification; iteration 2 keeps, per thread, a quality-weighted running mean of L2-normalized embeddings per speaker cluster (the quality weight is the capture-quality score of D-03 — effective duration is duration times quality — with the device's quality profile as a prior on each capture's weight) (an utterance joins the nearest cluster or opens a new one when its distance exceeds a threshold — online diarization), so evidence accumulates across utterances without retaining audio, mixed-speaker threads keep separate accumulators, and the dominant speaker of a thread is the cluster with the most weighted duration. Each cluster's accumulated embedding is scored against the whole matrix and, when a continuity prior names an expected speaker, additionally verified against that speaker (1-to-1); per-utterance scores are still produced for speaker-switch detection. Representation and enrichment (owner questions 2026-09-28): a thread is one conversation container; clusters are speaker tracks inside it, recorded per turn as a thread-local speaker_cluster_id and rendered in the app as speaker labels (a name once identified, otherwise "Speaker 2, unidentified") — a thread is never split by cluster. One ECAPA forward pass per utterance yields one embedding consumed by both the per-utterance identification (a read-only comparison in memory, no disk write) and the cluster accumulator (a vector and weight per cluster in memory, persisted with the thread at checkpoints and at thread end); the accumulator uses the same quality-weighted mean as the enrollment imprint, applied to a thread-scoped cluster. The stored imprint is enriched at session end (follow-up window expiry; see below), never per utterance: a cluster contributes to a user's stored voiceprint only if it resolved to that user at high certainty, the accumulated cluster signature itself passes a verification threshold against the stored imprint, quality-weighted duration exceeds a minimum, and the cluster shows no unresolved speaker conflict; the update is a single duration-weighted contribution — the cluster's mean embedding weighted by its total quality-weighted (effective) duration, which is mathematically the same result as applying its utterances one at a time, so there is no per-utterance imprint update (each voice turn's own embedding and capture statistics are still stored on the turn, D-03); a long session therefore carries proportionally more weight, as the algorithm intends, and there is no cap on that weight (owner ruling 2026-09-29, superseding the 1.10 "contribution weight is capped"); drift is guarded instead by a maturity-aware verification gate — the acceptance threshold is a configured curve over the imprint's accumulated effective duration (quality-weighted seconds, the same field the mean is weighted by — never wall-clock age or utterance count), loose while that total is small and tightening to the mature threshold as it grows, so a weak initial imprint (a congested voice, a poor microphone) is corrected quickly by clean later sessions rather than refusing them forever — and the weighted mean itself already moves a young imprint far and a mature one little; a session in which the speaker passed a pass-blurb is ground truth and contributes regardless of the cosine gate, subject only to cluster purity (no second speaker on the track); a drift monitor tracks each user's identification confidence over time and, on a declining trend or repeated pass-blurb successes with low cosine, offers a spoken re-enrollment; the displacement limit of 1.11 is withdrawn (owner question 2026-10-05: it was a weight cap by another name and would have blocked exactly the correction a weak imprint needs); multi-centroid imprints (several prototypes per user, matched by the best; the three mechanisms above adopted 2026-10-05) are a Phase 2 research item, triggered if environment variance proves the dominant source of low scores; centroid keying policy (2026-10-06): captures record both device and environment (D-03), so per-device and per-environment profiles are aggregations over the same rows and need no schema choice; centroids are keyed by device first (a fixed device is its environment), merged when two devices in one environment produce indistinguishable centroids, and split by environment for mobile devices that travel; the reference centroid is built from the highest-reliability captures, while each environment centroid is built from its own environment's captures with quality setting the weight, never the eligibility; the imprint is versioned so an enrichment can be rolled back, and the in-memory matrix row is refreshed atomically — one write per speaker per session instead of one per utterance, and no circular reinforcement from evidence still being used to identify. Bookkeeping (owner question 2026-10-05): the thread record stores, per cluster, a per-session summary (mean embedding, effective duration) and a contributed watermark; the thread-cumulative accumulator is the fold of those summaries and is reloaded on rejoin for identification only (thread prior, dominant speaker, Layer 1); at session end only that session's own summary is contributed to the imprint and marked, so a thread of one hundred sessions contributes one hundred times, each once, and earlier evidence is never resubmitted; the gate evaluates the session signature, with the thread cumulative as corroboration only. Thread-accumulator lifecycle: held in memory during a session, persisted with the thread record at session end, reloaded on rejoin, and deleted when the continuation horizon expires and the thread closes — derived, rebuildable state, never a long-term store; it serves thread binding (the continuity prior), corroboration of the session-signature gate, and the thread's own running identification (Layer 1 loading, dominant-speaker label, user tags on turns), and is never itself contributed to an imprint. Enrichment runs at session end (follow-up window expiry), not at thread end: a thread may stay open for rejoining across the continuation horizon, its cluster accumulators persisted with the thread and reloaded on rejoin, and each session contributes its own evidence once. Identity data lives outside the silo scheme (D-01). Carry-over; auth tiers Phase 2.
- C-05 Router/arbiter (S-01). Voice verdicts: {ignore | FSM event with slots | escalate}. Text verdicts: {start | queue | interrupt | FSM command}. Injection verdicts: {discard (voice-origin only) | queue | interrupt}. The router is the primary FSM driver and sees one utterance plus FSM state; the voice-slot model (S-02), holding Layers 0-3, may also propose transitions that need conversational context or that the router missed — the escalation valve that makes no misroute irreversible. Renders tiny in-workflow replies itself. Because the router already gates every voice turn, Layer 2 retrieval runs only on escalate verdicts, never on ignore or FSM-event verdicts. Two experiments, harness-gated (Phase 1-2): (a) the voice verdict may carry retrieval hints — entities, topic, active-project guess — produced within the same generation and consumed by C-07's Layer 2 topic slice at no additional model round-trip; adopted only if the recall slice improves; (b) a complexity flag in the same verdict (the Plano/Arch-Router pattern) as a fourth input to the voice-path latency gate; adopted only if the routing slice holds. Phase 1-3.
- C-06 FSM registry and validator. Statechart definitions with entry guards, states, slot schemas, legal transitions. The validator deterministically checks any proposed transition or slot update and, on rejection, returns a constraint hint to the component that proposed it (router, arbiter, or voice-slot model). Retries are bounded (two additional attempts); after the bound, the proposal is dropped with a logged trace and a neutral clarifying reply on the originating channel, voice or text (Q08, A13); confirmation ordering applies to slot-only updates as to transitions. A structured output is ratified or rejected as a whole: if any proposed slot update or transition is illegal, no sibling tool call executes and no sibling response text is delivered (owner answer Q08). Validation scope is workflow state (FSM slots and transitions); task status fields, counters, and logs are ordinary writes (Q07). Phase 1-2.
- C-07 Prompt builder. Assembles state-conditioned prompts in a fixed order so that the byte-stable part stays prompt-cached. Each layer is defined by what it carries and by how it is fetched. Layer 0 — what: persona (core directives, voice register, behavioral boundaries) and the tool registry for the slot; how: static text, byte-stable, prompt-cached, warmed once at boot, identical on every turn. Layer 1 — what: promoted durable facts about the identified speaker, their active projects and goals, and during a research session the research status board; two disclosure levels retained as a configurable distinction (owner decisions 2026-09-27 and 2026-09-28): Layer 1a, the workspace-visible facets (name, non-private preferences), and Layer 1b, the full standing-context summary — project names, goals, preferences, and the status board projection of the user's research tasks (task title, phase, progress, last step summary, estimate; never a result body, never silo-origin content outside an active silo session, F3) — both load as soon as the thread's cumulative voiceprint (C-04 accumulator) reaches high-certainty identification, which normally precedes three separately identified utterances; the three-consecutive rule remains the fallback when accumulation is unavailable, and the 1a/1b split is kept so the policy can be tightened later without a schema change; Layer 1b is a disclosure of the summary to an identified speaker, not an authentication (the owner considers nothing in Layer 1 sensitive, and a spoken Layer 1 summary is ordinary workspace transcript content readable by every workspace device, owner Q1 2026-09-28): Layer 2 project history, Layer 3 retrieval over user stores, and project actions still require the pass-blurb on the voice route; facts promoted from identification-only threads are held out of Layer 1b until confirmed (C-15); how: SQL keyed on user_id when C-04 resolves identity (mid-session if identification arrives late), status board refreshed per loop boundary. Layer 2, project slice — what: recent sessions of the active project, as verbatim recent turns under a token cap (2-4K tokens as a placeholder to be set by the harness's recall slice), with sessions older than the cap represented by their idle-window summaries plus pointers (C-24) that Layer 3 can expand to verbatim on demand; how: SQL keyed on project_id, loaded once when the active project resolves (active project in Layer 1 or explicit command), refreshed at session boundaries, and placed in the cache-stable prefix region after Layer 1 so it costs prefill once per session. Layer 2, topic slice — what: memories relevant to the current utterance from the stores the session's area may read (silo area: silo, then user, then workspace with descending weights; user area: user then workspace; workspace area: workspace only), weighted toward the active project; how: C-13 hybrid lexical + vector with Reciprocal Rank Fusion over the whole finalized utterance (lexical ranking is Postgres full-text ranking; BM25 via extension only if the recall slice demands it — owner answer Q05) (no keyword selection step: term weighting and the embedding do that work), run by deterministic code after the router verdict and before the voice-slot generation, only on escalated turns, with no additional model call to plan the retrieval, tens of milliseconds; deterministic sharpeners permitted without a model call: dictionary matching against ontology entities to trigger exact fact lookups, and appending the previous user turn for pronoun-heavy utterances. Frozen-snapshot rule: the topic slice is injected into this turn's prompt in a capped slot (top 5-8 snippets, a few hundred tokens) placed after the cached prefix, used for this turn and discarded on the next; only the verbatim dialogue persists in the window, so retrievals never accumulate. Layer 3 — what: anything beyond the standing and per-turn slices: whole-silo transcript search (full-text or trigram), fact lookups with SQL joins, document-node lookup, research-transcript access; how: single-shot tool calls the model requests through C-09, fast-class tools only on the voice path. Per turn, outside the layer numbering: active FSM state and slot schemas, local time and elapsed time since the previous turn. Authorization precedes ranking: an eligibility predicate (current principal, workspace memberships, owning scope, owner and sharing policy, assurance level, active silo session, and the Layer 1a/1b disclosure exception) decides which items may be read at all, and scope and area weights rank only the eligible items; every context item carries its source scope and is never relabeled to pass the check; the same predicate governs full-text, vectors, facts, document nodes, the semantic cache, prompt-prefix reuse, the status board, wiki and code-graph results, MCP responses, and outbound payloads (audit A03). A project name disclosed in Layer 1b does not authorize its project slice. Phase 1 (Layers 0-1 and the topic slice, text mode); Phase 2 (project slice and tiered loading on the voice path).
- C-08 Structured-output contract. JSON schema: slot_updates, transition, tool_calls, response_text, confidence; constrained decoding. Only response_text reaches TTS. For any output that proposes a transition, response_text is a draft: the spoken or written confirmation is produced only after the validator applies the transition, from an FSM template or a second short generation that sees the applied state, so success text never precedes ratification (I-14, Q08). Phase 1.
- C-09 Tool registry and executor. Opaque slot-bound tools; Docker-sandboxed execution with no agent access to the project root. Every registered tool carries a latency class: fast (SQL fact and join lookups, full-text and trigram search over transcripts, document-node fetch, semantic-cache lookup, single-shot lookups such as weather, timers, reminders, fact storage and recall) or slow (LLM-guided document-tree descent, web research — fetching and reading pages, multi-step — multi-document synthesis, anything multi-step). Web lookup — a single search-API query returning snippets, a few hundred milliseconds — is a fast-class single-shot tool eligible on the voice path within Budget B; web research is slow-class and research-only (owner decision 2026-09-27, A09). The voice slot's registry exposes fast tools only; the research slot's exposes both. The voice path allows at most one tool round per turn under Budget B (R-04); the structured output either answers or requests research, and a request that would exceed the budget becomes a research task. Latency classes are tentative until measured. Phase 2.
- C-10 MemoryStore. Postgres + pgvector + full-text search; tables: workspaces, silos, projects, user_silos, transcripts, facts (bi-temporal), documents, document_nodes, tasks, model_calls, manifests, traces, tunnels, blocked_pairs, capability_cards, feedback_events, panel_results. Backend-agnostic interface; every method takes a scope context (C-32). - C-33 Access control and sessions. Devices are registered with a device-bound secret at pairing and assigned to one workspace and to zero or more conversation groups; a workspace authorizes devices, apps, actions, and FSM functions individually (enrollment and voice cloning are separate authorizations). Pairing is by an issued device secret, never by network identity such as a MAC address (spoofable): a new device or a newly detected voice triggers a spoken request to the workspace administrator ("a new device is trying to connect — authorize it?"), and a yes plus the administrator's pass-blurb issues the secret or adds the person; static tokens in configuration serve until voice-approved pairing exists. Assurance levels: workspace (registered device), user (the "pass-blurb": Fawkes pushes one of a pre-recorded pool of two-to-three-sentence passages to the user's registered device — app push, SMS, or a paired screen — and asks the speaker to read it aloud, so possession of the device, the voiceprint over a passage long enough for a strong match, and rotating content that defeats replay are all checked at once; or device biometrics unlocking a device-bound key; or web sign-in), silo (a live user session plus a PIN as second factor — the PIN is never sufficient alone; after leaving the silo the user remains signed in at user level and re-enters the silo with the PIN alone while that session lasts; one active session per silo, device-exclusive, the newer device evicting the older). Read/write asymmetry: saving a conversation or task to the user's own store requires only high-confidence continuous identification, because the speaker is writing to their own memory; reading or retrieving from the user area requires the pass-blurb (or biometrics or web sign-in). Pass-blurb challenge protocol (A15): each challenge is issued with an identifier, expires after about a minute, is bound to the user, device, thread, and the action requested, is consumed on success and never accepted twice, and a passage is not reissued to the same user within a long interval; a response whose audio byte-matches a previously accepted response is rejected; attempts are limited and failures rate-limit; synthesized speech is the residual threat, mitigated by the pool size and by excluding voice from silo entry entirely, and its detection is an open measurement (Q-15). Evidence unit (A17): one physical utterance is one unit of identification evidence regardless of how many streams carried it (overlap binding deduplicates); the consecutive-identification count resets on a mismatching utterance or a thread break; a device "observed" an authentication only if its stream carried the pass-blurb utterance or was overlap-bound to the stream that did; authentication inheritance never arises from pooled confidence alone; revocation, expiry, or a speaker change invalidates cached Layer 1b content, permission-keyed cache entries, and pending private output; text clients authenticate by session and never by speech evidence. Authorization is evaluated per utterance: a device holds user-level authorization only while continuous speaker identification keeps matching the authenticated speaker: each utterance is served only at the assurance its own speaker holds, and the device's standing voice-derived authorization is revoked by thresholds rather than by a single foreign utterance (owner decision 2026-09-28) — three consecutive quality-sufficient utterances from a non-owner cluster on the same device drop the device to workspace level for the user area, two consecutive such utterances during a silo session lock the entire silo session — voice and text — pending the PIN, while the parent user-area sign-in remains valid (owner ruling 2026-09-29, superseding "two in total" and "voice access only"), and the parent user-area sign-in established by text, web, or app is never revoked by voice events — only a silo session built on it can lock; authorization is inherited by a device in the same conversation group that observed the authentication (its stream carried the pass-blurb or was overlap-bound to the stream that did), and — within the follow-up window only — by a group device that verifies the authenticated speaker's voice without having observed it (owner decision 2026-09-28, Q2; this supersedes the 1.8 wording "only by devices … that observed" for the window). Identification evidence belongs to the conversation thread, not the microphone: every device in the conversation group that hears the speaker contributes to one running identification score, so a device the speaker walks toward inherits the thread's accumulated confidence rather than starting from zero. Mechanism (owner question 2026-09-26): a new microphone's stream is bound to a thread by three kinds of evidence, in descending strength. (a) Acoustic overlap: if the new microphone hears the conversation while another is active, the same utterance appears on both streams with matching timing in the audio domain — time-aligned correlation of energy envelopes and voice-activity onsets and offsets, optionally a lightweight acoustic fingerprint — never a second transcript, because listen-along streams are not transcribed; interim-transcript matching occurs only during the brief handoff overlap when a listen-along stream is re-elected and becomes ASR-eligible (F2); the audio match is deterministic, needs no voiceprint, and works at poor signal-to-noise because it matches when speech occurred rather than who spoke, and it proves the streams share a physical source, so the thread's score carries over. (b) Continuity without overlap: a stream that begins shortly after the thread went silent on a neighboring microphone in the same conversation group, with topically continuous content, receives a provisional association — a hypothesis, not a confirmation — which turns the identification problem from 1-to-N (who is this, among all enrolled speakers, needing roughly ten seconds of audio) into 1-to-1 verification (is this still the hypothesized speaker, needing a sentence or two); the new stream's own utterances supply the evidence, confidence updates per utterance, and contradicting evidence drops the hypothesis and restarts full identification. (c) Every utterance's contribution is weighted by its quality (duration, voice-activity confidence, signal-to-noise ratio, as in the iteration-1 multi-factor scoring), so a distant or noisy microphone confirms slowly and never alone, and the three-consecutive-identification rule for Layer 1b counts only utterances of sufficient quality. Thread evidence accelerates identification and never authorizes: no user-area read occurs on continuity alone; at least one positive voice match on the new stream is still required, followed by the pass-blurb — except within the follow-up window in the same conversation group, where verification alone inherits the existing user-level authorization (the 2026-09-28 exception); silo access never inherits. Two people near one microphone produce two speaker tracks (clusters) with separate scores inside one thread (C-04); this is distinct from two genuinely independent conversations sharing a microphone, which the wake and session manager keeps as separate threads — both scenarios are Phase 2 tests. A speaker entering a room where another is talking binds per utterance to their own track and never merges into the other's. Idle timeouts and absolute lifetimes are configured separately per level (user hours, silo minutes). Every authentication event, scope transition, pairing, revocation, and silo entry writes an audit row. Unenrolled voices are matched transiently and never persisted as voiceprints; enrollment records consent (to be confirmed present when the enrollment FSM is ported). Accounts and roles (owner decisions 2026-09-27): each workspace has an administrator, who may browse every workspace in the app's workspace area (including workspaces they are not assigned to) and who alone may move mixed-speaker threads, but who cannot access other users' areas or any silo; a separate root account, distinct from the owner's daily user account, may access every database, table, user area, and silo. Root is usable only through an explicitly authenticated web or app session with its own password, separate from the workspace administrator's; voice can never invoke root; a root session ends by explicit sign-out or absolute lifetime and every action is audited (owner decision 2026-09-28, Q3); a second factor for root is proposed, not yet adopted. Each user registers a preferred device (a phone, whose notifications the paired watch mirrors) for unsolicited messages (P-21). Phase 2 (workspace and user levels), Phase 5 (web sign-in, silo sessions, second factor).

- C-34 Wake and session manager (Phase 2). Wake-word beacon collection and election, session-window and follow-up-window lifecycle, listen-along requests to group microphones, in-session quality scoring and hysteresis re-election, overlap binding, the continuity judge (deterministic: time gap, group adjacency, topical similarity → a prior over speakers), and binding events (D-12, P-20). ## 4. Data model (summary)

- D-01 Identity store, outside the silo scheme: Person (user_id, name, preference facets, preferred device, roles: user, workspace administrator, root), voice imprints, Device (device_id, time zone, endpoint type, mains-powered flag, listen-along eligibility, environment_id for fixed devices, quality_profile — running tier-1 signal statistics and tier-3 embedding reliability), Environment (environment_id, name, workspace, conversation group; a room, zone, or vehicle), user_silos membership with a default silo per user.
- D-02 Scope and silo layer, Tier A (migration 001): `workspaces` and `silos` tables, each with one seeded default; every content and derived table — and only those; identity, device, role, session, and configuration records keep their separate authority under D-01 — carries a non-null scope kind and scope id (`scope_kind` in workspace/user/silo, `scope_id`), with `silo_id` required exactly when the scope is a silo (supersedes the 1.4 wording "non-null silo_id on every table" now that projects may live in any scope); projects keyed `(scope_kind, scope_id, project_id)` and referenced by that composite triple, a project belonging to one scope for life; the scope pair included in every unique constraint and index prefix (content hash unique per scope); tunnels and blocked pairs share a single scope pair for both endpoints so a cross-scope link cannot be represented (supersedes the 1.7 wording "silo_id in every unique constraint" and "single silo_id column", A02); semantic cache, traces, manifests, and outbound payloads carry the silo; leakage tests are permanent. Tier B (deferred until a second silo exists): list partitioning of vector and full-text tables by silo; row-level security keyed to silo under a non-owner role with a transaction-scoped setting (row-level security keyed to *user* arrives in Phase 5 regardless); per-silo roles; instance pin to an allowed silo set. Tier A costs about an hour and nothing at runtime; Tier B is real friction and delivers nothing at one silo.
- D-03 Turn: id, event_id (runtime-generated, unique, the idempotency key — Q01), scope kind and id, project_id, owner_user_id (null while unidentified), identified_user_id and identification_confidence (set by continuous voice identification without changing the scope — see below for the audio research columns added 2026-10-06), device_id, environment_id (the fixed device's environment, or the room resolved for a mobile device from the election or presence beacon; nullable), capture_quality (JSON: speech-to-noise ratio, clipping rate, effective bandwidth, reverberation estimate, learned quality score when computed), speaker_embedding (the utterance's ECAPA vector, stored for every voice turn so per-device reliability, centroid research, and identification replay need no audio), conversation_thread_id, speaker_cluster_id (thread-local diarization label), task_id (nullable; ordinary turns have no task, A22), role, text (verbatim), recorded_at (UTC), local_tz, model_call_id, trace_id.
- D-04 Fact: id, scope kind and id (silo_id when silo-scoped), subject, predicate, object, facet (v1 vocabulary: fact, preference, decision, event, task-state), valid_from, valid_to, recorded_at, source, salience components, superseded_by.
- D-05 Document, DocumentNode (tree nodes with summaries and spans, stored as Postgres rows), content hash unique per scope, provenance, structure score, index status.
- D-06 Task: scope kind and id (silo_id when silo-scoped), plan, status, checkpoints, status board, blackboard notes, cost rollup, originating channel.
- D-07 ModelCall: model, slot, tokens in/out/cached, cost, duration, time-to-first-token, thinking setting, scope kind and id.
- D-08 Tunnels and blocked pairs: one scope pair (kind and id) shared by both endpoints, so a cross-scope link cannot be represented (supersedes "one silo_id column", F1). Manifest and Trace rows carry the scope pair. CapabilityCard: model, quant, serving config, fingerprint, per-slice scores, latency percentiles, field observations, version, evaluated_at.
- D-09 FeedbackEvent: turn_id, task_id, kind (thumbs_up, thumbs_down, explicit_correction, re_ask, confirm, abandon), source channel, payload, silo_id, recorded_at. PanelResult: task_id, models, per-model tokens/loops/duration, judge rubric grades, verdict, arbiter strategy.
- D-10 Scope model (owner answers Q03, Q04, Q09, Q11). Two axes on every content row: the *area* (workspace, user, silo) that determines the assurance level required to read it, and the *owner* (a user, or shared). Workspace-area rows are shared among the workspace's devices and hold unidentified and workspace conversations, workspace-shared facts (household reminders, shared lists), and workspace projects. User-area rows are owned by one user and readable only by that user after user-level authentication; personal conversations are never readable by another user, in any area. Silo-area rows carry a silo id: documents in a silo's designated project folder are shared among silo members; conversations and research transcripts inside a silo are owned by the user who produced them and readable only by that user within an active silo session. Standing-context facets carry a visibility marker: a workspace session loads the workspace-visible subset (Layer 1a) after one positive identification and the full standing-context summary (Layer 1b, including the status board projection of the user's research tasks) once the thread's cumulative voiceprint reaches high-certainty identification — three consecutive positive identifications being the fallback when accumulation is unavailable — as a disclosure to an identified speaker and not as authentication (A01, owner 2026-09-28); facts promoted from identification-only threads carry an unconfirmed flag and are excluded from Layer 1b until confirmed (A16). Retrieval reads the current area's stores plus the areas below it with descending weights (silo → user → workspace). Projects, research tasks, documents, and databases are scoped to the area they were created in; a table may be limited to one workspace, shared across workspaces, or moved to the user level. Tasks inherit their creating scope, and results wait as durable pending deliveries collected on any of the user's text devices at the required assurance level; voice access to a user-scoped result requires user authentication; silo results are viewable only inside the silo area on the actively authenticated device.
- D-11 Devices, groups, and threads. Device: device_id, workspace_id, endpoint type, time zone, pairing secret reference, conversation groups. ConversationGroup: devices among which an authenticated conversation may continue without re-authentication (a home group; a car is not in it). ConversationThread: a cross-device continuation detected by topic and timing before voice identification resolves; carries the pooled identification score, the count of consecutive quality-sufficient positive identifications, the binding evidence for each member stream (overlap, continuity hypothesis, or confirmed voice match), and the hypothesized speaker while unconfirmed; a thread is workspace-scoped until promoted (P-16). Session: user or silo, device, assurance level, issued_at, idle timeout, absolute lifetime, exclusive flag for silos. PendingDelivery: task_id, user_id or null, scope, channel type, originating device and thread, delivery id, claimed_by, acknowledged_at, state (pending, claimed, delivered, expired).
- D-12 Microphone-handling matrix (owner decisions 2026-09-26/27). New input on a microphone is handled by three conditions — acoustic overlap with an active stream, membership in the active thread's conversation group, and whether a session or its follow-up window is open:

| Overlap | In group | Session or follow-up open | Stream | Transcription | Thread | Identification | Authorization inherits |
|---|---|---|---|---|---|---|---|
| Yes | Yes | Yes | Listen-along stream already open | On re-election (or on speech if the session just ended) | Bound deterministically by overlap | Thread score carries over; per-utterance verification continues | Yes, at the thread's level |
| Yes | No | Yes | Not open (non-group microphones never listen along); wake word required | After wake | Overlap, if observed on the device's own session stream, binds the thread for the record only | Cold 1-to-N | No |
| No | Yes | Yes | Listen-along or follow-up stream already open | On local speech detection | Continuity judge proposes a thread (time gap, adjacency, topic) | Verification against the hypothesized speaker with the thread prior; the full matrix is scored in parallel so a wrong hypothesis resolves in seconds | Yes, once verification passes |
| No | No | Yes | Wake word required | After wake | Continuity judge may associate turns post hoc for the record | Cold 1-to-N | No; re-authenticate for user-area reads |
| No | Yes | No | Wake word required | After wake | Continuity judge with a decayed prior that reaches uniform at a horizon | Weak prior; verification as evidence allows | No; the follow-up window is the inheritance window |
| No | No | No | Wake word required | After wake | Cold; topic-only post-hoc link at most | Cold 1-to-N | No |
| Yes | any | No | Impossible: overlap requires a concurrent session | — | — | — | — |

Three parameters govern the matrix and are configured separately, in the configuration area and never in code: the follow-up window (wake-less listening and the authorization-inheritance window; start short), the thread-continuation horizon (rejoining a thread after a wake word by topical similarity plus voice verification; longer, tuned by experiment), and the continuity prior's decay horizon (identification acceleration only, bounded by the continuation horizon).

## 5. Pathways

- P-01 Voice turn, no FSM active. C-01 → C-02 → C-03 → C-04 → C-32 → C-05. Ignore: persisted as noise, no response. FSM event: P-02. Escalate: C-07 → S-02 → (any proposed transition validated by C-06) → C-31 speaks response_text → C-12 persists turn, trace, cost → C-15 judges promotion.
- P-02 FSM workflow. Entry guard fires — utterance-driven via C-05 (primary), utterance-driven via S-02 when the cue needs conversational context or the router missed it, or signal-driven via C-04. C-05 handles subsequent turns; C-06 validates each transition; workflow state and slots are keyed by user, scope, and workflow instance, shared across the user's devices, with at most one active instance per workflow family per user, stale concurrent updates rejected by a version check, each applied state is retained as an immutable versioned snapshot (an append-only history for audit and rollback) while the live instance advances by creating new versions — "immutable" never means the live workflow is frozen (convergence review 2026-09-28, BC-74), and resumption on a second device only after continuous voice identification matches there; enrollment and authentication workflow state lives in the identity store outside content scopes (Q07). Enrollment is a workspace-scoped workflow that creates an identity: it runs against a provisional user record created at its first turn, captures the voiceprint, and records consent; it grants no user-area access. (The 1.5 text's optional passphrase step is removed: authentication uses the pushed pass-blurb of C-33, so an enrolled identity with a registered device is authenticatable without a memorized phrase.) An illegal proposal (for example, "advance to record_pangram" while the name slot is empty, or entering voice_clone while enrollment is active) returns a constraint hint to the proposer, which retries within the bound; after the bound, the proposal is dropped and traced. Exit persists results via C-12.
- P-03 Text-channel message. → C-32 (scope from the signed-in area) → C-05 as arbiter → start (create Task, start C-18) | queue (outbox) | interrupt (cancel event) | FSM command (validated by C-06; illegal commands return to the arbiter, never to the voice slot). Never discarded. Result returns as text (P-14).
- P-04 Research task lifecycle. C-18 plans; loops over tool calls (each a loop boundary); at each boundary: drain outbox, refresh status board, checkpoint, check pending counter (wait up to timeout). Retrieval via C-13/C-25/C-19; escalation via C-22; completion writes cited synthesis and cost rollup; delivery per P-14 or P-05.
- P-05 Voice-initiated research. S-02 answers provisionally and starts a Task with originating channel = voice. Later voice turns add notes (blackboard) or imperatives (command queue). On completion or a material update or self-correction, C-18 raises a correction event through C-16. Delivery (owner decision 2026-09-27, A14): if the originating thread has had activity within the last 60 seconds — measured against its most recent activity, however many times it paused and resumed — the result is spoken on the last device used in that thread — for a workspace-scoped task whether or not the speaker was identified; for a user-scoped task only if that device still holds the required assurance for that user (a speaker change or expiry before completion blocks playback even inside the window); for a silo-scoped task only on the actively signed-in silo device — a recent thread is a delivery destination, not a permission grant (F3); if nobody responds or the room is empty, the result remains visible in the thread in the app; if the thread has been silent for more than 60 seconds and the speaker was never identified, the result is recorded in the thread; if the thread is silent and the speaker was positively identified, an unsolicited notification goes to the user's preferred device (P-21), and the result is spoken when the user opens the channel. A voice-initiated result is never rendered as text on a channel the user did not open.
- P-06 Mid-flight injection and interrupt. Input arrives while C-18 is generating → inbox → pending counter increments → C-05 rules {discard (voice-origin only) | queue | interrupt}. Queue: outbox. Interrupt: cancel event → watcher cancels generation and aborts the vLLM request → the partial output is retained in the transcript as aborted-generation evidence marked invalid, never dispatched as a tool call or delivered as an answer → injection appended → C-18 resumes and resteers itself. A cancellation that lands during a tool request leaves that tool's outcome unknown; the outcome is reconciled from the tool's own record and the tool is never re-run automatically (A12). Boundary wait: if pending > 0 at a boundary, C-18 waits up to the timeout, then proceeds treating undecided items as queued. Each message receives exactly one disposition; a verdict arriving after the timeout is logged and ignored; every cancel names a task id and a generation id and can never hit a later generation; interrupt discards the stale generation's output but does not undo tool side effects already committed, which the research model sees in its transcript on resume; a side-effecting tool is never re-run automatically after a cancel or restart (Q10).
- P-07 Read-down. Status board refreshed every boundary and injected into S-02's Layer 1 on every voice turn during an active research session; deep detail via Layer 3 tools reading the research transcript.
- P-08 Ingestion. Source adapter → C-12 (typed idempotency per C-12, provenance, scope and project stamps) → source rows and their search vectors committed and derived jobs recorded in one transaction → acknowledgement → fan-out from the job table: vectors, C-17 structure scoring → tree build (idle-time) or lazy-only; C-15/C-26 fact extraction and contradiction check; wiki update queued (Phase 4).
- P-09 External escalation. C-22 policy triggers → payload builder produces extracted text/JSON/Markdown (local OCR via S-03 vision if needed) → silo assertion → budget gate → remote call → D-07 records tokens/cost → response returns into the calling pipeline with provenance marked external.
- P-10 Identity and startup. Boot: speaker matrix loaded, Layer 0 warmed, capability cards loaded. New client: device presents its pairing secret and registers time zone; unpaired devices are rejected. Identification states: unidentified, voice-identified; assurance levels: workspace, user, silo (R-12, C-33). Phase 0 uses a seeded, identified test user with default workspace and silo membership (Q03).
- P-11 Memory promotion and consolidation. Per turn: C-15. Idle windows: C-24, C-26 reconciliation (Phase 4), eval runs on fingerprint change.
- P-12 Panel mode (Phase 4). Critical task → both models (or Qwen self-fusion) run the identical spec or vote on extracted decisions → arbiter strategy → verdict and candidates recorded → result returns to the requesting pipeline.
- P-13 Heads-down mode (Phase 4+). Mode switch → voice-slot model unloaded → coding model or Harness-1 loaded → voice slot rebinds to a Qwen register → tools rebind by slot → exit reverses.
- P-14 Text response and pending delivery. Every text-channel task returns text to the originating client, appended to the originating thread as a follow-up ("following up on your question from earlier…"), whether or not the client is still connected (A14). Completion and delivery are separate records: a finished result waits as a durable pending delivery (D-11) with a delivery id; a reconnecting client at the required assurance level claims it, acknowledges it, and the record moves to delivered; a lost acknowledgement re-offers the same delivery id so clients deduplicate; two clients reconnecting at once resolve by the claim; delivery re-validates assurance at delivery time, and a result whose scope the client no longer holds stays pending; text sessions are chats listed per user. Workspace-scoped tasks with no identified user deliver to the originating thread, readable by every device in the workspace. Voice-initiated tasks return through P-05. A voice question about a text-initiated task is answered by voice from the status board; if the task is user-scoped, the status board projection is available at Layer 1b to an identified speaker (the adopted exception) while any result body or deeper detail requires user authentication, if silo-scoped only the actively authenticated silo device may hear a summary (Q11).
- P-15 Cross-silo movement. No in-place move: export from the source silo, write a manifest, re-ingest into the destination silo as new rows with an opaque text pointer to the source; approval is a pluggable policy (the owner in Fawkes).
- P-16 Workspace conversation, identification, and promotion (Q09). A registered device's utterances enter the workspace store unidentified. Continuous voice identification runs on every utterance; a conversation thread may be recognized across devices by topic and timing before identity resolves. When identification reaches high confidence, the turns are tagged with the identified user and Layer 1a — the workspace-visible subset of standing context (name, non-private preferences) — loads; Layer 1b — the full standing context, including private projects and goals — loads together with 1a once the thread's cumulative voiceprint reaches high-certainty identification (three consecutive positive identifications is the fallback trigger), and the conversation becomes fully personalized, though it stays workspace-scoped. A question about a personal project before Layer 1b has loaded triggers the pass-blurb. User-area retrieval (Layers 2 and 3 over user-scoped stores) still requires user authentication; saving the thread to the user area does not. A pass-blurb given inside a workspace-scoped thread forks the thread: the continuation becomes a new user-scoped thread linked to the workspace thread at the fork point, so replies that carry private retrieved content never enter the workspace store and the mixed-speaker promotion rules are untouched (owner decision 2026-09-28, resolving Q-17). On "save this to my account" or "make this private", high-confidence continuous identification suffices (a write to the speaker's own store), and the whole thread is moved to the user area with its original timestamps and an audit row; thereafter it is readable only at user level. Promotion mechanics (owner decisions 2026-09-27, A18): a thread moves as a unit, including every speaker's turns; a thread with more than one identified speaker may be moved only by the workspace administrator — a voice request from anyone, the administrator included, is answered "there are multiple speakers in this conversation; only the administrator can move it," and the administrator may reply "override" and give the pass-blurb; in the app, a non-administrator sees "move to my profile" and, for a mixed thread, the same notice with a cancel button, while the administrator sees "move to a profile," the notice with cancel and override (no further authentication, the app session being authenticated), and a searchable list of the workspace's users; "duplicate" copies a thread so copies can be moved to several profiles. The move is one transaction: source turns, derived rows, facts, and pending jobs change visibility together, the thread's project reference is remapped to a user-scoped project or cleared (projects are scope-immutable), and a delayed retry cannot recreate a public copy. After promotion, Layer 1 is updated with the owner's own turns weighted highest; preferences stated by another speaker may be recorded when relevant, and because every identified turn stores its speaker, "who set that preference?" retrieves the exact turn and speaker. Never-identified workspace turns remain in the workspace store under the retention policy.
- P-17 User authentication and follow-me authorization (R-12, C-33). The auth FSM pushes a rotating pass-passage from the pre-recorded pool to the user's registered device and asks the speaker to read it aloud; a passing voiceprint match over the passage plus correct content raises the device's assurance to user level; device biometrics unlocking a device-bound key or web sign-in do the same for that device. Authorization is checked per utterance: while continuous identification on a device keeps matching the authenticated speaker, user-area stores are readable there; revocation follows the thresholds in C-33 (three consecutive non-owner utterances for the user area; two consecutive during a silo session lock that silo session, voice and text, pending the PIN, the user-area sign-in surviving; the parent user-area sign-in established by text, web, or app is never revoked by voice); devices in the same conversation group that observed the authentication inherit it, and within the follow-up window a group device that verifies the speaker inherits it without observation; devices outside the group, or beyond the window, do not. Idle and absolute timeouts end the session; a speaker change, revocation, or expiry invalidates cached Layer 1b content and any pending private output for that device (A17); every transition is audited.
- P-18 Silo session lifecycle. Silo entry requires a live user session established by web or app sign-in (a voice-authenticated or biometric-only session is not eligible) plus the silo PIN as second factor — never the PIN alone — and opens a device-exclusive session; all silo access is by text through the signed-in web or app session, and documents enter a silo's shared folder only through that session, each addition recorded with a manifest (owner clarification 2026-09-27, A19); two consecutive non-owner utterances heard on the silo session's voice channel lock the entire silo session, voice and text, until the PIN is re-entered, without ending the user-area sign-in (owner ruling 2026-09-29); conversations may be moved from the workspace to a user area by voice but never into a silo by voice; leaving the silo keeps the user session, and re-entry within it needs only the PIN; voice access to the silo is available only over the WebSocket created from that signed-in session, the scope asserted server-side on every request; a new device entering the silo evicts the previous session; the session locks after a short idle timeout (re-entry by the second factor) and ends at an absolute lifetime; any other voice pipeline asked about silo-scoped data replies that the information may be protected and directs the user to sign in.
- P-19 Cloud escalation policy (Q12). Cloud use is disabled until the owner enables a scoped policy (tasks, tiers, monthly budget, per-task cap). The primary trigger is complexity above a threshold, with an explicit user request as an override of the complexity gate but never of the budget; local confidence is a secondary signal. Each escalation is a single stateless request carrying a context bundle assembled locally (extracted text, relevant facts, the question), with prompt caching for repeated bundles within a task; Claude acts as a subagent inside a locally hosted task, never as the host of a session. Every remote turn is stored locally with timestamps, tokens, cost, and timing exactly like a local turn. A denied call makes no external request, says so, and continues locally.
- P-20 Wake word, election, sessions, and listen-along (owner decisions 2026-09-26). Every device runs an on-device wake-word detector; nothing streams until it fires. On detection each device sends a beacon (timestamp, detector confidence, energy); Fawkes collects beacons for a short window (about 200-300 ms, closing early when one beacon dominates or all group devices have reported, and hidden behind the command the speaker is already uttering, which every candidate device buffers from the wake word), elects the dominant microphone, opens its session stream (VAD, ASR, identification), and asks the mains-powered microphones in the dominant device's conversation group to open listen-along streams — audio in, no transcription, nothing stored except binding events; battery devices do not listen along by default. During a session Fawkes computes speech activity and quality on every open stream and re-elects with hysteresis, switching the ASR to the already-open stream with a brief overlap; beacons are not used after the cold election. After a reply, group microphones stay in a wake-less follow-up window (local VAD gating; configurable, start short); speech in the window continues the session and applies D-12; outside the group or after the window, the wake word is required. Three windows are separately configurable and never hard-coded (owner decision 2026-09-28): the follow-up window (wake-less listening and authorization inheritance; on the order of a minute), the thread-continuation horizon (how long a thread may be rejoined after a wake word by topical similarity plus voice verification; minutes to hours, to be tuned by experiment), and the session timeouts of C-33. A rejoined thread continues its existing cluster accumulators rather than resetting them; rejoining after the follow-up window associates turns and supplies the identification prior but inherits no authorization. Only the dominant stream is transcribed and ingested; listen-along streams yield binding events only.
- P-21 Unsolicited delivery to a preferred device (owner decision 2026-09-27). When Fawkes must reach an identified user who is not in an active thread (a finished voice-initiated task, a scheduled task, an alert), it sends a push notification to the user's preferred device ("new research result", "Fawkes has a message"); tapping it opens a channel to Fawkes, which then speaks; a paired watch mirrors the phone's notification. Phones and watches cannot be made to play audio or record unsolicited, so the notification is the bridge; a Fawkes-owned satellite in the user's last-known room may speak unsolicited because Fawkes controls it; an Android device running the Fawkes foreground service may also speak unsolicited where the platform allows. Delivery re-validates assurance when the channel opens.

## 6. Interfaces and seams

- X-01 OpenAI-compatible `/v1/chat/completions`: the only way any pipeline talks to any language model, local or remote, with provider adapters behind it; speech models, the speaker matcher, and the embedder use their own typed in-process interfaces and are not X-01 traffic (A07).
- X-02 MemoryStore interface: the only way any component reads or writes memory; every method takes a scope context (C-32).
- X-03 ingest(): the only write path.
- X-04 MCP server: the only way external agent hosts reach Fawkes memory or tools.
- X-05 Tool registry: slot-bound; identical surface for any model in a slot.
- X-06 Event bus contract: inbox/outbox/pending/cancel primitives; swappable for a real message bus without changing callers.

## 7. Invariants

- I-01 Only response_text reaches TTS; reasoning never leaks to speech.
- I-02 No workflow state (FSM slots and transitions) mutates without validator approval; rejected proposals return to their proposer with a hint, bounded; a proposal is ratified or rejected as a whole.
- I-03 No LLM round-trip inside voice retrieval: Layers 0-2 assemble by deterministic code after the router verdict and before the voice-slot generation, with no model call to plan retrieval; SQL hops are permitted, reasoning hops are not; retrieval hints produced inside the router's own verdict are not a round-trip.
- I-04 ASR text reaches research only via the voice pipeline; text-channel messages are never discarded.
- I-05 The arbiter triages; the research model resteers.
- I-06 Verbatim rows are never deleted or rewritten by summarization; manifests accompany every transformation.
- I-07 All timestamps are UTC time-zone-aware; rendering is per session.
- I-08 Every model call has a ModelCall row with tokens and cost.
- I-09 Derived stores may be dropped and rebuilt from their authority at any time: Fawkes-memory derivatives from Postgres; repository-derived code graphs from the versioned repository at a recorded revision (A08).
- I-10 A phase exit test never leaves the test suite.
- I-11 Response modality follows input modality: voice in, voice out; text in, text out; background results return through the channel that started the task.
- I-12 No row, cache entry, tunnel, prompt item, or outbound payload crosses a silo boundary; the only movement between silos is the export-and-re-ingest of P-15 under authorized contexts; leakage tests gate every phase exit.
- I-13 Authorization is evaluated per utterance against continuous speaker identification; no device holds user-level access for a session as a whole, and no voice pipeline other than an actively authenticated silo session reads silo-scoped data. Writes to a user's own store need identification; reads need authentication, with one named exception: Layer 1b discloses the standing-context summary (including the status board projection) to a speaker identified at high certainty by the thread's cumulative voiceprint (three consecutive identifications as fallback), which authorizes nothing further (A01).
- I-14 Success text never precedes ratification: a confirmation of a state change is produced only after the validator applies it.
